title: Task — Lazy Asynchronous Work
description: Model asynchronous operations as lazy, infallible functions that execute only when called.
---

JavaScript `Promise` instances execute eagerly upon creation and can reject with untyped values (`unknown`). This makes it difficult to compose async workflows before execution or track errors in type signatures.

`Task<A>` is a function accepting an optional `AbortSignal` and returning an infallible `Deferred<A>`:

```ts
type Task<A> = (signal?: AbortSignal) => Deferred<A>;
```

Because `Task` is a function, execution is deferred until invoked. Because `Deferred<A>` is typed to never reject, failures are tracked explicitly in return types via `Task.Result<E, A>`.

```ts
import { pipe } from "@nlozgachev/pipelined/composition";
import { Task } from "@nlozgachev/pipelined/core";

const getTimestamp = Task.from.sync(() => Date.now()); // Task<number>

// 1. Compose the pipeline — nothing executes yet
const formattedTime = pipe(
  getTimestamp,
  Task.map((ts) => new Date(ts).toISOString()),
); // Task<string>

// 2. Explicitly execute by invoking the function
const timeString = await formattedTime();
```

## Creating Tasks

We create `Task` values depending on whether the computation is already resolved, synchronous, or asynchronous:

```ts
// Resolving immediately with a constant value
const constantTask = Task.make(42); // Task<number>

// Wrapping a lazy synchronous computation
const readClockTask = Task.from.sync(() => performance.now()); // Task<number>
```

Because standard Promises in JavaScript can reject, `Task.tryCatch` is the canonical intake for asynchronous operations where you want to handle any failure immediately with a fallback value so the resulting `Task<A>` is guaranteed never to fail:

```ts
// Trapping errors with a fallback handler
const loadConfig = Task.tryCatch(
  () => configStore.get("default"),
  { onError: () => DEFAULT_CONFIG },
); // Task<Config>
```

## Transforming, Sequencing, and Side Effects

We can transform and chain our asynchronous blueprints while they are still in their lazy, unexecuted state.

### Transforming values with `map`

`map` describes how the resolved value should change once the Task eventually runs, returning a new `Task` without triggering any execution:

```ts
const double = (n: number) => n * 2;

const doubledTask = pipe(
  Task.make(5),
  Task.map(double),
); // Task<number>

const result = await doubledTask(); // 10
```

### Sequential chains with `chain`

When a transformation itself returns another `Task`, we use `chain` to execute them sequentially and flatten the resulting context:

```ts
const getSessionUserId = (): Task<string> => Task.make("user_abc");

const loadUserPreferences = (userId: string): Task<Preferences> =>
  Task.tryCatch(
    () => preferencesService.get(userId),
    { onError: () => DEFAULT_PREFERENCES },
  );

const userPrefs = pipe(
  getSessionUserId(),
  Task.chain(loadUserPreferences),
); // Task<Preferences>

const prefs = await userPrefs(); // Loads userId first, then loads preferences
```

### Combining independent tasks with `apply`

When you have a curried function inside a `Task` and want to feed multiple independent `Task` arguments into it, `Task.apply` executes the tasks in parallel and applies their resolved values:

```ts
const formatSummary = (region: string) => (uptimeMs: number) =>
  `[${region}] Uptime: ${uptimeMs}ms`;

const summaryTask = pipe(
  Task.make(formatSummary),
  Task.apply(detectRegionTask),
  Task.apply(readUptimeTask),
); // Task<string>
```

### Side effects with `tap`

`Task.tap` runs a side-effect callback on the resolved value without altering the `Task` output:

```ts
const auditedConfigTask = pipe(
  loadConfig,
  Task.tap((cfg) => console.info("Loaded config version:", cfg.version)),
);
```

## Concurrency Controls

Unlike raw Promises, which require manual coordination using `Promise.all` or `Promise.race`, `Task` provides composable combinators for parallel, raced, or sequential execution.

### Parallel execution with `all`

`Task.all` runs an array of Tasks simultaneously and collects all results into a typed tuple:

```ts
const [config, user] = await Task.all([
  loadConfigTask,
  loadUserTask,
])();
```

The return type is structurally matched to your input: passing `[Task<Config>, Task<User>]` yields a `Task<[Config, User]>` tuple.

To prevent overwhelming resources, provide `{ concurrency }` to constrain how many tasks execute at any given moment:

```ts
const userTasks = userIds.map((id) => loadUserTask(id));

// Executes at most 3 tasks concurrently using an internal worker pool:
const users = await Task.all(userTasks, { concurrency: 3 })();
```

### Raced execution with `race`

`Task.race` starts multiple Tasks simultaneously and resolves with the outcome of whichever Task completes first, automatically aborting the remaining in-flight tasks via their `AbortSignal`:

```ts
const fastestSource = Task.race([
  loadFromPrimaryCache,
  loadFromSecondaryCache,
]);

const data = await fastestSource(); // Whichever cache responds first
```

### Sequential queueing with `sequential`

When execution order matters, or when running tasks in parallel would trigger race conditions or overload resources, `Task.sequential` executes an array or tuple of `Task`s one at a time in submission order:

```ts
const results = await Task.sequential([
  acquireLockTask(resourceId),
  processPayloadTask(resourceId),
  releaseLockTask(resourceId),
])();
```

## Operational Utilities

### Delayed execution with `delay`

`Task.delay` introduces a timed pause before the Task executes:

```ts
import { Duration } from "@nlozgachev/pipelined/types";

const delayedGreeting = pipe(
  Task.make("Hello"),
  Task.delay(Duration.seconds(1)),
);
```

### Enforcing deadlines with `timeout`

`Task.timeout` converts an infallible `Task<A>` into a fallible `Task.Result<E, A>`, resolving to `Err(onTimeout())` if the task does not complete within the specified `Duration` and aborting the inner `AbortSignal`:

```ts
import { Duration } from "@nlozgachev/pipelined/types";

const boundedComputation = pipe(
  runHeavyIndexRebuild,
  Task.timeout({
    duration: Duration.seconds(5),
    onTimeout: () => "INDEX_REBUILD_TIMED_OUT" as const,
  }),
); // Task.Result<"INDEX_REBUILD_TIMED_OUT", IndexStats>
```

### Standard cancellation with `abortable`

`Task.abortable` wraps a promise factory, yielding a managed `Task` alongside a shared `abort` function. Invoking `abort()` immediately cancels any active, in-flight execution:

```ts
const { task: searchIndex, abort } = Task.abortable(
  (signal) => searchLocalIndex(query, signal),
);

// If user types rapidly:
input.addEventListener("input", async () => {
  abort(); // Cancel the active search request
  const results = await searchIndex(); // Start a fresh search
});
```

Calling `task()` while a previous invocation is still active will automatically abort the previous run.

### Progress tracking and diagnostic labels: `withProgress` and `withLabel`

`Task.withProgress` invokes a callback with `0` immediately before the task starts and `1` when it resolves. `Task.withLabel` attaches a read-only `.label` property to a `Task`, preserving the literal label string in editor hover tooltips:

```ts
const backupTask = pipe(
  exportDatabaseSnapshot,
  Task.withProgress((ratio) => updateProgressBar(ratio * 100)),
  Task.withLabel("database-snapshot-backup"),
);

console.log(backupTask.label); // "database-snapshot-backup"
```

### Ending pipelines with `run`

When composing inline pipelines, `Task.run` allows you to execute the Task at the terminal end of the `pipe` chain, returning a `Deferred` value that resolves to the output, and accepting an optional `AbortSignal` for external cancellation:

```ts
const controller = new AbortController();

const configUrl = await pipe(
  loadConfigTask,
  Task.map((cfg) => cfg.apiUrl),
  Task.run(controller.signal),
);
```

## Polling and Repetition

`Task` provides built-in utilities to repeat executing a task, designed naturally around the guarantee that Tasks are infallible.

`repeat` executes a Task a fixed number of times, collecting all outcomes:

```ts
import { Duration } from "@nlozgachev/pipelined/types";

const readings = await pipe(
  readSensorTask,
  Task.repeat({ times: 5, delay: Duration.seconds(1) }),
)();
```

`poll` re-runs a Task on an interval until the returned value satisfies a predicate, returning that final value:

```ts
const readyState = await pipe(
  checkStatusTask,
  Task.poll({
    until: (status) => status === "COMPLETED",
    delay: Duration.seconds(2),
    attempts: 10, // Cap attempts to avoid infinite loops
  }),
)();
```

## The Task Family

While `Task<A>` is designed for operations that never fail, typical real-world async tasks involve network or database requests that can yield errors or empty results. For these, we use specialized namespaces within `Task`.

### Task.Result

`Task.Result<E, A>` represents a fallible async task, equivalent to `Task<Result<E, A>>` under the hood.

#### Creating and converting `Task.Result`

Construct a `Task.Result` directly with `make.ok` and `make.err`, wrap a throwing or rejecting promise factory with `tryCatch`, or lift existing values via `from.Result`, `from.Maybe`, and `from.nullable`:

```ts
import { Maybe, Result, Task } from "@nlozgachev/pipelined/core";

const okTask = Task.Result.make.ok(42);
const errTask = Task.Result.make.err("UNAUTHORIZED");

const fromNullableTask = pipe(
  process.env.API_URL,
  Task.Result.from.nullable(() => "Missing API_URL"),
);

const fromMaybeTask = pipe(
  Maybe.make.some("token_xyz"),
  Task.Result.from.Maybe(() => "Missing token"),
);

const fromResultTask = Task.Result.from.Result(Result.make.ok("ready"));
```

For network calls and fallible I/O, use `Task.Result.tryCatch`:

```ts
const fetchProfile = (userId: string): Task.Result<string, User> =>
  Task.Result.tryCatch(
    (signal) => fetch(`/users/${userId}`, { signal }).then((r) => r.json()),
    { onError: (error) => `Could not fetch user: ${error}` },
  );
```

To discard the error channel and convert a `Task.Result<E, A>` into a `Task.Maybe<A>`, use `Task.Result.to.Maybe`:

```ts
const optionalProfile: Task.Maybe<User> = pipe(
  fetchProfile("123"),
  Task.Result.to.Maybe,
);
```

#### Transforming, recovering, and extracting `Task.Result`

`Task.Result` mirrors the full `Result` combinator surface over async execution (`map`, `mapError`, `bimap`, `chain`, `apply`, `ensure`, `tap`, `tapError`, `recover`, `recoverUnless`, `match`, `getOrElse`, `run`):

```ts
const loadUserBanner = (userId: string): Task<string> =>
  pipe(
    fetchProfile(userId),
    Task.Result.ensure(
      (user) => user.isActive,
      (user) => `User ${user.id} is deactivated`,
    ),
    Task.Result.map((user) => user.name.trim()),
    Task.Result.mapError((err) => `[Auth] ${err}`),
    Task.Result.tap((name) => console.info(`Loaded active user: ${name}`)),
    Task.Result.tapError((err) => console.warn(err)),
    Task.Result.recoverUnless(
      (err) => err.includes("deactivated"),
      () => Task.Result.make.ok("Guest User"),
    ),
    Task.Result.match({
      ok: (name) => `Welcome, ${name}`,
      err: (err) => `Access denied (${err})`,
    }),
  );
```

When combining independent fallible tasks via a curried function, `Task.Result.apply` runs them in parallel:

```ts
const mergeUserAndQuota = (user: User) => (quota: number) => ({ user, quota });

const accountWithQuota = pipe(
  Task.Result.make.ok(mergeUserAndQuota),
  Task.Result.apply(fetchProfile("123")),
  Task.Result.apply(fetchQuota("123")),
);
```

#### Cancellation and Timeouts in `Task.Result`

When sequencing multiple `Task.Result` steps, `Task.Result.chain` propagates the `AbortSignal` down the line automatically. You can also enforce a deadline on any `Task.Result` using `Task.Result.timeout`, and execute the pipeline using `Task.Result.run(signal)`:

```ts
import { Duration } from "@nlozgachev/pipelined/types";

const fetchReport = (reportId: string): Task.Result<string, Report> =>
  pipe(
    Task.Result.tryCatch((sig) => initiateJob(reportId, sig), { onError: String }),
    Task.Result.chain((job) =>
      Task.Result.tryCatch((sig) => downloadData(job.url, sig), { onError: String })
    ),
    Task.Result.timeout({
      duration: Duration.seconds(10),
      onTimeout: () => "Report generation timed out",
    }),
  );

const controller = new AbortController();
const result = await pipe(
  fetchReport("report_42"),
  Task.Result.run(controller.signal),
);
```

#### Retrying fallible tasks with `Task.Result.retry`

When network operations or database queries suffer transient failures, `Task.Result.retry` automatically re-evaluates the task according to a `RetryPolicy`:

```ts
import { Duration, RetryPolicy } from "@nlozgachev/pipelined/types";

// Constant delay policy (3 attempts, 500ms apart)
const constantPolicy = RetryPolicy.constant({
  attempts: 3,
  delay: Duration.milliseconds(500),
});

// Exponential backoff policy with randomized jitter
const exponentialPolicy = RetryPolicy.exponential({
  attempts: 5,
  initial: Duration.milliseconds(100),
  factor: 2,
  jitter: true,
});

const resilientFetch = pipe(
  fetchProfile("123"),
  Task.Result.retry(exponentialPolicy),
);
```

To fail fast on permanent client errors while retrying transient server errors, pass a `when` predicate:

```ts
type HttpError = { status: number; message: string };

const isTransient = (err: unknown): boolean =>
  typeof err === "object" && err !== null && "status" in err && (err as HttpError).status >= 500;

const transientFetch = pipe(
  fetchProfile("123"),
  Task.Result.retry(exponentialPolicy, { when: isTransient }),
);
```

#### Non-short-circuiting batching with `allSettled`

When evaluating multiple independent fallible requests in parallel, `Task.Result.struct` short-circuits on the first error encountered. If you need all tasks to run to completion regardless of individual failures (such as health check probes or bulk batch processing), use `Task.Result.allSettled`:

```ts
import { Result } from "@nlozgachev/pipelined/core";

const healthChecks = [
  checkDatabase,
  checkRedis,
  checkExternalGateway,
];

// Returns Task<readonly Result<CheckError, HealthStatus>[]>
const outcomes = await Task.Result.allSettled(healthChecks)();

for (const outcome of outcomes) {
  if (Result.is.ok(outcome)) {
    console.log("Service operational:", outcome.value);
  } else {
    console.error("Service degraded:", outcome.error);
  }
}
```

### Task.Maybe

`Task.Maybe<A>` represents an asynchronous operation that may yield nothing, equivalent to `Task<Maybe<A>>`.

You can construct a `Task.Maybe` with `Task.Maybe.make.some`, `Task.Maybe.make.none`, `Task.Maybe.tryCatch` (which turns rejections into `None`), or lift values via `Task.Maybe.from.Maybe`, `Task.Maybe.from.nullable`, `Task.Maybe.from.Result`, and `Task.Maybe.from.Task`:

```ts
import { Task } from "@nlozgachev/pipelined/core";

const lookupUser = (id: string): Task.Maybe<User> =>
  Task.Maybe.tryCatch((signal) =>
    fetch(`/users/${id}`, { signal }).then((r) => (r.ok ? r.json() : Promise.reject()))
  );
```

`Task.Maybe` supports `map`, `chain`, `apply`, `filter`, `tap`, `recover`, `match`, `getOrElse`, `to.Result`, and `run`:

```ts
const resolveActiveUserEmail = (userId: string): Task.Result<string, string> =>
  pipe(
    lookupUser(userId),
    Task.Maybe.filter((user) => user.isActive),
    Task.Maybe.map((user) => user.email),
    Task.Maybe.tap((email) => console.debug("Found active email:", email)),
    Task.Maybe.recover(() => lookupBackupEmail(userId)),
    Task.Maybe.to.Result(() => `No active email found for user ${userId}`),
  );
```

### Task.Validation

`Task.Validation<E, A>` represents an asynchronous validation check that accumulates multiple errors across parallel checks, equivalent to `Task<Validation<E, A>>`.

Create a `Task.Validation` using `make.passed`, `make.failed`, `make.failedAll`, `tryCatch`, or lift existing containers via `from.Validation`, `from.Result`, `from.Maybe`, and `from.nullable`:

```ts
import { Task } from "@nlozgachev/pipelined/core";

const checkUsernameAvailable = (username: string): Task.Validation<string, string> =>
  Task.Validation.tryCatch(
    async (signal) => {
      const response = await fetch(`/api/usernames/${username}/available`, { signal });
      if (!response.ok) throw new Error("Username is already taken");
      return username;
    },
    { onError: () => `Username "${username}" is not available` },
  );
```

`Task.Validation` provides `map`, `mapError`, `apply`, `struct`, `tap`, `tapError`, `recover`, `recoverUnless`, `match`, `getOrElse`, `to.Result`, `to.Maybe`, and `run`:

```ts
const registerAccount = (username: string, email: string) =>
  pipe(
    Task.Validation.struct({
      username: checkUsernameAvailable(username),
      email: checkEmailDomainAllowed(email),
    }),
    Task.Validation.mapError((err) => `[Registration] ${err}`),
    Task.Validation.tapError((errors) => {
      logger.warn(`Async validation failed with ${errors.length} errors`);
    }),
    Task.Validation.to.Result((errors) => errors.join("; ")),
  );
```

## Lazy Task Memoization: Task.memoize

Because `Task` blueprints are lazy thunks, calling a task multiple times will re-trigger the underlying async computation every time.

`Task.memoize` (as well as `Task.Result.memoize`, `Task.Maybe.memoize`, and `Task.Validation.memoize`) creates a memoized task that executes the operation at most once on the first call and caches the resolved result for all subsequent calls:

```ts
const loadToken = Task.memoize(
  Task.tryCatch(
    () => readAuthToken(),
    { onError: () => "ANONYMOUS_TOKEN" },
  ),
);

// First invocation triggers token resolution:
const token1 = await loadToken();

// Subsequent invocations return the cached result instantly without re-evaluating:
const token2 = await loadToken();
```

## Accumulating values: bind / bindTo

When you need to perform multiple sequential asynchronous operations and gather their results into a single object, nesting `chain` and `map` inside pipelines can become hard to read.

You can use `bindTo` and `bind` to cleanly accumulate asynchronous values key-by-key in a flat, readable pipeline. These helpers are available across `Task`, `Task.Result`, and `Task.Maybe`.

`bindTo` wraps an asynchronous value into the pipeline's accumulator object:

```ts
pipe(
  Task.make(42),
  Task.bindTo("value"),
); // Task<{ value: number }>
```

`bind` runs a new asynchronous operation using the accumulated object and attaches the result to a new key:

```ts
const userProfile = pipe(
  getUser(userId), // Task.Maybe<User>
  Task.Maybe.bindTo("user"),
  Task.Maybe.bind("prefs", ({ user }) => getPreferences(user.id)),
  Task.Maybe.bind("theme", ({ prefs }) => getTheme(prefs.themeId)),
); // Task.Maybe<{ user: User; prefs: Preferences; theme: Theme }>
```

If any step fails (yielding `None` in `Task.Maybe` or `Err` in `Task.Result`), the entire pipeline short-circuits and propagates the failure immediately.

## Combining async records: struct

While `bind` is ideal for sequential steps where a later step depends on the output of a prior step, sometimes you have a set of independent asynchronous tasks that you want to combine into a single object. For this, you can use the `struct` helper, which is available on `Task.Result`, `Task.Maybe`, and `Task.Validation`.

`struct` combines a record of async tasks into a single task holding a record of success values. Under the hood, **it evaluates all tasks in parallel** while forwarding the `AbortSignal` down to each sub-task.

### With Task.Result
If any individual field resolves to an `Err`, the entire struct short-circuits to that error. If multiple fields fail, `Task.Result.struct` returns the first error encountered in key order:

```ts
const profileTask = Task.Result.struct({
  user: getUser(userId),
  permissions: getUserPermissions(userId),
  status: Task.Result.make.ok("active"),
}); // Task.Result<string, { user: User; permissions: Permission[]; status: string }>
```

### With Task.Maybe
Evaluates fields in parallel, resolving to `Some` record if all succeed, and returning `None` immediately if any task resolves to `None`:

```ts
const profileTask = Task.Maybe.struct({
  user: lookupUser(userId),
  preferences: loadPreferences(userId),
}); // Task.Maybe<{ user: User; preferences: Preferences }>
```

### With Task.Validation
Evaluates validations in parallel and **accumulates all validation errors** across all failed branches, rather than short-circuiting:

```ts
const validationTask = Task.Validation.struct({
  username: checkUsernameAvailable(username),
  email: checkEmailDomainAllowed(email),
}); // Task.Validation<string, { username: string; email: string }>
```

## Running Tasks at boundaries

Because a `Task` is a function, you run it by invoking it (or passing it to `Task.run(signal)`). Invoking a `Task<A>` yields a `Deferred<A>`, which you can `await` directly within any standard `async/await` block:

```ts
const value = await fetchProfile("123")(); // Ok(user) or Err(error)
```

If you are interfacing with external libraries or frameworks that strictly require a standard `Promise` instance, you can convert the `Deferred` value using `Deferred.to.Promise`:

```ts
import { Deferred } from "@nlozgachev/pipelined/core";

const profilePromise = Deferred.to.Promise(fetchProfile("123")()); // Promise<Result<string, User>>
```

## Problems it solves

- **Composing lazy asynchronous workflows**: In background workers and server endpoints, asynchronous pipelines often involve multiple sequential steps (such as acquiring auth tokens, querying profile data, fetching permission lists, and writing audit records). Native promises execute eagerly upon creation. `Task` encapsulates asynchronous operations as lazy descriptions, enabling modular pipeline composition and transformation before initiating network or I/O work.
- **Coordinated concurrency and fallback racing**: When aggregating data across distributed backends or caching layers, applications need fine-grained concurrency control. `Task` provides structured combinators like `Task.all` for parallel fan-out, `Task.race` for racing primary against fallback sources, and `Task.sequential` for queue execution, all while preserving functional purity.
- **Compiler-enforced async error handling with `Task.Result`**: Network calls and disk I/O naturally produce domain failures. Standard `Promise.reject` discards TypeScript type information, allowing unhandled rejections to bubble up. `Task.Result` pairs lazy asynchronous execution with typed errors, ensuring the outer task always resolves safely while forcing callers to handle specific failure variants.
- **Time-bound operations and scheduled polling (`Task.timeout`, `Task.delay`, `Task.repeat`, `Task.poll`)**: Wrapping external network calls with timeout boundaries typically involves race boilerplate with `setTimeout` and cleanup listeners. `Task.timeout` and `Task.Result.timeout` attach strict duration limits returning typed `Result` errors on expiration, while `Task.delay`, `Task.repeat`, and `Task.poll` configure scheduled interval polling cleanly.
- **Asynchronous optionality with `Task.Maybe`**: When loading cached tokens or reading optional database settings asynchronously, missing entries are expected. `Task.Maybe` threads async execution and optional absence together, allowing callers to map, chain, and recover without nested promise-and-null checks.
